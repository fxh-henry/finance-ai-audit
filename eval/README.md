# 消融实验（eval/）

**目的**：用数字回答四个问题，而不是靠嘴上争。

| 对比 | 回答的问题 |
|---|---|
| C 组本身 | 纯硬编码规则能做到什么程度 |
| B − D | 结构化裁决值多少 |
| A − B | 防幻觉校验值多少 |
| E − A | 反思机制值多少 |

**注意**：这一整套不修改主流程任何代码。

---

## 一、文件清单

| 文件 | 作用 | 烧 token |
|---|---|---|
| `legacy_text_verdict.py` | 冻结的改造前解析器（D 组基线）。**不要修改** | 否 |
| `groups.py` | 五组后处理的实现 | 否 |
| `run_model_once.py` | 对用例跑一次模型，固化 `runs/*.json` | **是** |
| `replay.py` | 读 `runs/`，算五组结论与指标 | 否 |
| `inject_hallucination.py` | 注入已知幻觉，测校验层召回率与误伤率 | 否 |
| `inject_trap_text.py` | 注入「陷阱句」（含否定嵌套句），测结构化裁决的净收益 | 否 |
| `make_cases.py` | 生成 24 条用例（A 制度反推 / B 报销单一致性 / T 语义陷阱） | 否 |
| `make_demo_runs.py` | 生成演示用 runs，验证脚本能跑通 | 否 |
| `cases/` | 用例集（需自备） | — |
| `runs/` | 真实模型输出（跑批生成） | — |
| `runs_demo/` | 演示数据（**不是真实实验数据**） | — |
| `reports/` | 指标输出 | — |

---

## 二、工作流

```bash
# 第 1 步（唯一烧 token 的一步，每个用例只跑一次）
python -m eval.run_model_once --cases eval/cases --out eval/runs

# 第 2 步（不烧 token，可反复跑）
python -m eval.replay --runs eval/runs --out eval/reports/ablation.json

# 第 3 步（不烧 token）
python -m eval.inject_hallucination --runs eval/runs --out eval/reports/hallucination.json

# 第 4 步（不烧 token）——陷阱句注入，含「否定嵌套句」单独一族
python -m eval.inject_trap_text --runs eval/runs --out eval/reports/trap.json

# 想先看脚本长什么样，不烧 token
python -m eval.make_demo_runs
python -m eval.replay --runs eval/runs_demo
```

**为什么模型只跑一次**：五组共用同一份 `runs/`，差异只来自后处理层，
不会被模型的随机性掩盖。这也是"结论翻转率"能单独测量的前提。

## 三、用例格式（`cases/*.json`）

```json
{
  "case_id": "case_001",
  "source": "制度反推",
  "note": "上海住宿480元，部门经理标准500元，应判合规",
  "label": "通过",
  "label_reason": "第十四条：上海(一线)部门经理500元/天，480<=500",
  "is_adversarial": false,
  "employee_id": 2,
  "invoice_data": { "发票号码": "...", "价税合计小写": "480.00", "...": "..." },
  "expense_form": { "expense_type": "住宿费", "ext_fields": {"city": "上海", "nights": 1} }
}
```

- `label` 只能是 `通过` / `不通过`，没有确定金标准的用例**不要放进来**（回放会自动跳过未标注用例）
- `is_adversarial` 为 true 的会单独统计（对抗样本子集），因为它们在简单样本里会被稀释
- `employee_id` 决定职级，住宿费的标准档位由它决定

**标签来源建议按这三个来（前两个零主观）：**

1. **制度反推**：拿住宿标准表反向造「刚好合规 / 超标 20%」的成对样本，答案由制度唯一确定
2. **故障注入**：拿真实发票程序化制造违规（超标、跨月、连号、拆分、抬头错），负样本自带标签
3. **少量人工标注**：只标规则做不了的语义类（事由与发票不匹配、费用类型选错）

## 四、三个已经踩过的测量陷阱（务必写进报告的方法论部分）

### 陷阱 1：D 组的基线必须是"改造前"的实现
`utils/audit_verdict.py` 里的文本解析器**已经被加固过**（先遮罩否定词、再取最后出现位置），
实测能正确解析陷阱句。如果 D 组直接调它，D 组会表现得和结构化方案差不多，
实验必然得出「结构化裁决提升 0%」—— 那是自证，不是测量。
所以 `legacy_text_verdict.py` 保留了改造前的实现，**不要修**。

### 陷阱 2：C 组必须拿到所有能硬编码的规则
如果 C 组只跑基础校验、不给它费用标准，C 组会被人为削弱，AI 的"增量"就被虚高了。
所以 `group_C` 把 12 项基础校验 + 6 项风控 + 费用标准全部用上 —— **凡是能硬编码的都给它**。
（实测结果：在规则能判的用例上，C 组和 AI 打平，AI 的增量只出现在语义判断上。）

### 陷阱 2 附：C 组必须保留「转人工」这一态
制度里本来就没写金额标准的费用（餐饮费、材料费），规则层的正确反应是
「不敢判 → 转人工」，而不是「不通过」。如果把 `passed=None` 硬算成不通过：

- 合规的单子会被冤枉成违规（例如材料费），C 组在这些样本上会「看起来判对」，
  其实理由完全不对；
- 「规则判错」和「规则不敢判」混在一起，AI 的增量就说不清了。

所以 `group_C` 返回三态，`replay.py` 单独统计转人工条数与转人工率，
并额外给一个 **敢判准确率**（只在该组敢下结论的样本上算）。
报告里这两个数要一起给：转人工率高说明规则覆盖不足，敢判准确率高说明规则可信。

另外记一个已经修掉的真实缺陷：表单里的费用类型叫「交通费」，
而费用标准工具的分支判断写的是「市内交通费」，两处对不上会导致
交通费永远查不到 80 元/天的标准、永远转人工。修法是在
`audit/expense_standard.py` 里加一张 `EXPENSE_TYPE_ALIASES` 别名表，
统一在一个地方做口径归一。

### 陷阱 3：不能用 `run_expense_form_audit` 的返回值直接当 runs
`pipeline.run_expense_form_audit` 会把 `verdict["verdict"]` 原地改写成校验层最终采用的结论。
如果拿它当 runs 存下来，B 组读到的就是"事后"结论 → **B 组 == A 组** →
实验得出「防幻觉校验收益 0 个百分点」。
所以 `run_model_once.py` 自己在**校验层改写之前**把原始裁决存下来。

### 附：误伤率的分母必须是"干净样本"
如果模型本来就判错了，校验层报警是它该做的事。
把这类样本算进"误报"，误伤率会虚高到 80% 这种程度。
`inject_hallucination.py` 只把「模型结论与金标准一致、且非对抗」的样本计入误伤率分母，
同时单独披露全样本报警率。

## 五、指标口径

- 差值一律写成 **"+X 个百分点"**，不要只写相对提升百分比。
  （82% → 94% 应写"+12 个百分点，相对提升 14.6%"，只写"提升 14.6%"是包装）
- 30 个用例时，1 条 = 3.3 个百分点，所以要**同时给绝对值和百分比**（"30 个里判对 27 个"）
- 样本量 < 100 时结论是趋势性的，必须在报告里主动写明，别等评委问
- 召回率和误伤率**必须一起给**：一个"永远报警"的校验层召回 100%，但毫无用处

## 六、演示数据说明

`runs_demo/` 里的模型输出是**手工构造**的，只为让脚本能在不烧 token 的情况下跑通，
**不是真实实验数据，不要引用其中的数字**。

它覆盖的情形：
- `demo_01` 合规 → 五组都应对
- `demo_02` 超标 → 五组都应对
- `demo_03` 陷阱句（否定嵌套）→ **D 组会判反**，其余对
- `demo_04` 模型幻觉（工具判超标、结论写通过）→ **B 组错，A 组被校验层救回**
- `demo_05` 反思触发但结论不变 → A 与 E 一致

## 七、陷阱句注入的实测数字（24 条用例，共 216 条注入文本）

两族分开统计，因为翻车机理不同，混在一起会互相稀释。

### 第一族：5 种基础措辞（每条用例 5 条，共 120 条）

| 组 | 构成 | 判对 | 准确率 |
|---|---|---|---|
| D_on_injected | 旧解析器（读注入后的自然语言） | 40/120 | 33.3% |
| B | 结构化裁决（不读自然语言） | 21/24 | 87.5% |
| A | 结构化 + 防幻觉校验 | 21/24 | 87.5% |

- 结构化裁决净收益：**+54.2 个百分点**（A − D_on_injected）
- 错误放行 70 条（放行率 100%）、误伤 10 条（误伤率 20%）——两个方向必须一起报
- 按措辞分解：分点核验式 100%，工具叙事式 / 条款查询式 / 叙述式各 42%，
  合规陈述式与（真值不通过侧的）分点核验式 0%

### 第二族：否定嵌套句（每条用例 4 条，共 96 条）

| 项 | 数字 |
|---|---|
| 旧解析器判对 | **0/96（0.0%）** |
| 错误放行（真值不通过 → 判成通过） | 56 条，放行率 100% |
| 误伤（真值通过 → 判成不通过） | 40 条，误伤率 100% |

这一族的结果是**定义性的**，不是意外：这些句子构造出来就是为了击败字面子串匹配。

- 真值「不通过」侧写「不予通过 / 无法通过 / 不能予以通过 / 不应通过」——
  句子里根本没有「不通过」三连字，旧解析器 `find("不通过")` 返回 -1，直接判成通过
- 真值「通过」侧写「不存在……不通过的情形」这类双重否定——
  旧解析器按「谁先出现」判成不通过
- 结构化裁决读的是枚举字段，对措辞完全免疫，所以 B / A 两组在这两族上数字不变

### 方法论提醒（必须写进报告）

旧解析器的缺陷是「文本属性」，不是「用例属性」。
实测模型输出的固定风格是开头就给结论（「❌ 审核不通过」），
此时「不通过」的起始位置比它内部的「通过」早 1 个字符，旧解析器恰好判对 ——
靠造用例的自然触发率就是 0，实验会得出「结构化裁决提升 0 个百分点」的假结论。
所以必须用注入法给可控数字，这也是本目录 `inject_*.py` 存在的理由。
