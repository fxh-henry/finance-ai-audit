一、项目背景

1.1 政策背景：数电票的法定原件是 XML，不是图片

全面数字化电子发票（下称数电票）在全国推广后，有一个关键事实常被忽略：XML 才是法定原件，PDF 与版式文件在法律意义上只是阅读件。

这件事的技术含义是：如果系统仍按「上传图片 → OCR → 存图」的老路走，它一开局就丢掉了最准确的那份数据，把后续所有判断都建立在二次识别的误差上。因此本作品把「XML 直解析」作为默认路径，只有拿到照片时才降级到 OCR。

1.2 业务背景：审核的重心应当前移

高校财务处与中小企业出纳的编制普遍偏紧。一张差旅报销单上，要核对抬头、税号、金额勾稽、住宿标准、是否重复报销……单张 3–8 分钟，一天看不了多少张。

但仔细拆开就会发现：其中绝大多数判断本来就有唯一答案（金额加不加得起来、有没有超标、号码有没有重复），不该占用财务的时间；真正需要人来判断的，只有「这笔消费的性质是什么」这一小部分语义问题。

于是本作品的核心判断是：

把有唯一答案的判断交给程序，把需要理解语义的判断交给 AI，并且让 AI 的每一条结论都能被程序核对。

这三句话构成了整个作品的技术骨架，也是它与「把单据全丢给大模型」的同类方案的分野。

1.3 一句话定位

面向高校与中小企业的数电票智能预审 Agent —— XML 原件直解析，规则先卡住硬伤，RAG 引用制度原文，Agent 给出可追溯、可追问的审核结论。定位为预审助手，不宣称替代财务终审。

1.4 与现有方案的差异化

对比维度 常见做法 本作品的做法 带来的差别

二、痛点问题

痛点 现在怎么做 后果
原件与识别不准 拍照 / PDF 再 OCR 号码、税额出错，后续所有结论都建立在错数据上
硬伤靠人眼 抬头、税号、金额勾稽逐项看 漏检重复报销、过期票；单张 3–8 分钟
制度检索靠翻文档 财务口头解释 同案不同判，员工反复改单
异常行为难发现 连号、拆单、临界金额靠经验 风险事后才暴露，事后追责成本高
结论不可追问 驳回只写「不符合规定」 咨询占满财务工作时间

这些痛点的共同结构：一张报销单上同时存在两类判断 ——

  • 确定性问题：金额对不对、是否超标、是否重复。答案唯一，失误形式是漏检。
  • 语义问题：这笔聚餐算不算业务招待、事由与发票内容是否对得上。答案依赖理解，失误形式是误判。

两类错误的成因完全不同，需要不同的技术手段。而现有方案往往用同一种手段处理全部（全丢给人，或全丢给模型），这正是痛点长期存在的根本原因。

三、需求分析

3.1 从痛点反推的四项硬需求

# 需求 为什么必须满足
1 识别要准 能拿到法定原件就不用 OCR；数据错了，后面全错
2 能算的不问模型 金额勾稽、超标与否有唯一答案，模型算错一个数整张结论就废了
3 要理解语义的才交给模型 这是规则写不完的部分，也是 AI 真正必须出场的地方
4 结论必须能被追问 每条结论都要能回答「凭什么」，并指出依据来自哪个工具、哪条制度

第 4 条是这套系统与「黑盒 AI」的分界线，也直接决定了后文技术方案里必须有防幻觉校验层。

3.2 关键技术判断：划定确定性边界

既然确定性问题与语义问题要分开处理，就必须明确一条边界，并且让程序去强制执行它，而不是靠提示词自觉：

归属 判断内容 由谁裁决
确定性侧 金额勾稽、明细汇总、单价核对、日期期限、号码格式、重复检测、税率、抬头税号 纯代码规则（毫秒级、结果唯一）
确定性侧 住宿 / 交通 / 伙食的金额标准核算 纯函数工具（唯一数值来源）
确定性侧 重复 / 连号 / 拆分 / 临界 / 高频 / 行为画像 纯 SQL 风控
语义侧 事由与业务的相关性、费用类型是否与票面一致、结论如何解释 Agent + 大模型

边界由校验层执行：一旦模型的结论与工具返回值矛盾，直接拦截或退回重查。

3.3 非功能需求

维度 要求 落实方式

稳定 单张异常不能影响整批 多张上传逐张处理；识别失败的发票照样生成卡片、置顶并附失败原因

四、目标用户群体与功能需求

4.1 三类角色

角色 核心诉求 对应功能
报销员工 上传发票、看预审结果、填单、被驳后知道怎么改 发票上传、我的票夹、发票详情、报销单填写
财务初审 看规则结果、风控亮灯、Agent 依据，决定放行或退回 我的报销单、报销单详情（含轨迹与校验报告）

4.2 可验收的功能需求

  1. 上传数电票后 1 分钟内给出基础合规结论，并逐项列出通过 / 不通过。
  2. 可一次上传多张，每张独立成卡，有问题的自动置顶。
  3. 提交报销单时自动运行 6 项行为风控。
  4. 终审结论必须携带「用了哪个工具、引用了哪条制度」。
  5. 员工可针对本张发票追问，回答必须能展开制度原文。
  6. 基础校验不通过的发票不允许进入填单环节（准入闸门）。
  7. 发票号码由系统从票夹带出，用户不手填。

4.3 功能边界（本作品不做什么）

  • 不替代银行回单、预算占用、银企支付。
  • 不承诺图片发票 100% 识别率（演示以 XML / 版式 PDF 为准）。
  • Agent 结论是预审建议，最终入账仍由财务确认。

   最终裁决 ──▶ 报销单详情（结论 + 推理轨迹 + 校验报告）

6.2 三条设计红线

红线一：金额不交给大模型算。 所有数值判定都在纯函数里完成，模型只负责判断费用类型、决定调用哪个工具、把结论解释给人听。校验层是这条边界的执行者——模型结论一旦和工具返回值矛盾，直接拦截。

红线二：结论不靠文本猜测。 早期实现让模型输出一段自然语言，程序再用「关键词谁先出现」去猜结论。实测反例：

输入：我通过调用费用标准工具核对后确认，该笔住宿费超标，审核不通过。
旧逻辑输出：通过            ← 一张超标发票被放行

现在结论被定义为 Pydantic 枚举字段，模型在解码阶段只能往 verdict 里填「通过」或「不通过」。结论从「需要猜的文本」变成「可以直接读的字段」。

红线三：没有条款依据，不许判「不通过」。 制度门禁规定：判「不通过」却给不出制度条款 → 硬拦截，改为「无依据 → 转人工」。这把「引用溯源」从界面装饰升级成了硬约束。

6.3 关键实现

识别层：数电票 XML 直读结构化字段；版式 PDF 用 pdfplumber 提取文字块坐标，找表头行后用各列中心点划分列边界，再按 y 坐标聚行还原明细表；对 PDF 中「数量单价」被粘成一个长串的脏数据，用穷举切分求 数量 × 单价 ≈ 金额 的最小误差解。多张上传时按文件 SHA1 指纹缓存，只解析真正的新文件。

校验层：12 项基础合规 + 6 项行为风控，全部纯代码。风控覆盖重复报销、连号发票、拆分报销、金额临界（审批阈值 95% 以上）、高频报销（部门人均 2 倍）、员工行为画像。

制度层：知识库为 Markdown，按标题层级分块（最大 300 字、块间重叠 2 句）；BM25（专有名词加权）与向量检索双路召回后加权融合，返回条款原文与出处，让「依据」可被引用、可被点击展开。

Agent 层：ReviewAgent 基于 LangGraph ReAct 循环，挂载费用标准工具与制度检索工具；AgentTrace 逐步记录思考、工具调用参数、工具返回原文与最终结论，一份数据两用——页面渲染时间轴，校验层逐条对账。ConsultAgent 负责帮助中心问答，携带本张发票的上下文。

后处理层：

  • 结构化裁决：结论、费用类型、理由清单、证据链、条款引用、置信度、是否转人工，全部固化为字段。证据的 source 只能填 5 个白名单来源之一，fact 中的数字必须与来源返回值完全一致。
  • 13 项防幻觉校验：结论取值合法 / 证据来源合法 / 工具调用可溯源 / 结论与证据自洽 / 结论未遗漏工具判定 / 风控高危已被吸收 / 金额可溯源 / 条款引用可溯源 / 通过需有证据 / 条款门禁（不通过需依据）/ 条款门禁（通过需计算）/ 人工确认已吸收 / 置信度水平。
  • 反思机制：分流（挑出可澄清的矛盾）→ 指令（要求追加检索、补齐参数）→ 收敛（第二轮必须复检，且没有新证据就不许放宽结论）。与校验层共享同一份判据，避免两处口径漂移；只给一次机会，卡住成本。

6.4 效果验证

我们为 AI 与各校验层建立了可复现的评测（eval/，不修改主流程任何代码）。

用例集：24 条，全部有制度唯一确定的金标准。其中 8 条为制度金额类（住宿城市 × 职级 × 金额），12 条为语义一致性类（票面与报销单是否对得上），4 条为语义陷阱类（金额全合规，唯一违规点在语义）。其中 12 条为对抗样本——金额落在标准内，只看数字永远判不出来。

AI 相对纯规则引擎的增量

类别 条数 纯规则判对 转人工 Agent 判对 增量
制度金额类 8 7 0 7 +0.0pp
语义一致性类 12 3 3 10 +58.3pp
语义陷阱类 4 0 2 4 +100.0pp
合计 24 10（41.7%） 5 21（87.5%） +45.8pp

对抗样本子集（12 条）：纯规则 0/12（0%），Agent 12/12（100%）。

这张表说明了架构的合理性：金额类的活，规则干得和 AI 一样好（7/8 打平）；语义类的活，规则只有 18.8%，AI 达到 87.5%。 规则层对没有标准可依的费用类型返回「转人工」而不是硬判，避免冤枉合规单。

结构化裁决的价值（陷阱句注入，120 条文本）：旧字符串位置解析 40/120（33.3%），结构化裁决 21/24（87.5%），净收益 +54.2 个百分点；其中错误放行（真值不通过被判成通过）70 条，放行率 100%。

否定嵌套句专项（96 条文本）：旧解析器判对 0/96。真值「不通过」写成「不予通过 / 无法通过 / 不能予以通过」——句中根本没有「不通过」三连字，字符串匹配直接判成通过；真值「通过」写成「不存在……不通过的情形」——双重否定被按位置判成不通过。结构化裁决读枚举字段，对措辞完全免疫。

防幻觉校验的价值（注入 101 处已知幻觉）：任意报警 101/101（100%），硬拦截 42/101（41.6%），干净样本误伤 0/9（0%）。硬拦截只对能交叉核对的幻觉类型生效，语义类幻觉仅告警不拦截——这是有意的保守设计，宁可提示也不误改。

成本：单用例平均 59.3 秒；消融实验的额外 token 消耗为 0（五组共用同一份模型输出，差异只来自后处理层）。

6.5 稳定性与效率

  • 分层拦截：基础校验不通过就不进模型，既省钱，也避免模型被脏数据带偏。
  • 失败可见：识别失败或校验不过的发票照样生成卡片、置顶并附失败原因，不静默丢弃。
  • 增量识别：按内容指纹缓存，重复上传不做重复解析。
  • 可复现：评测与主流程完全解耦，任何时候都能重跑并复现文中每一个数字。

效率口径（如实标注测量边界）

环节 耗时 来源
单张基础合规校验（12 项） 毫秒级 纯函数，无需网络
单张 Agent 终审（含模型调用与制度检索） 平均 59.3 秒 本作品 24 条用例实测

需要说明的是：预审并不能替代人工终审。它的价值在于把「有唯一答案的判断」整体从人工环节移除，让财务只看真正需要判断的那部分。

七、作品功能说明

每项写清三件事：功能是什么 / 没有 AI 会怎样 / AI 的增量在哪。

AI 在作品中的核心作用（总览）

AI 不是这里的装饰，也不是「把单据整体丢给大模型」。它恰好出现在规则做不到、而判断又必须做的位置：

AI 出场点 承担什么 为什么规则替代不了 被什么约束
Agent 终审 判断事由与业务的相关性、费用类型是否与票面一致 语义判断无法穷举成 if-else 结构化裁决 + 13 项防幻觉校验
事由语义审核 判断报销事由与发票内容、费用类型三者是否一致 同上，属语义判断 不通过时弹窗拦截；结果带缓存
工具调度 自主决定调费用标准工具还是制度检索、参数怎么填 不同单据需要的依据不同 工具调用全轨迹留痕，校验层逐条对账
结论解释 把「超标 80 元」翻译成员工能懂的话与整改建议 生成式表达 其中金额必须与工具返回值完全一致
自主纠错 发现矛盾后追加检索、修正结论 事前无法预知所有矛盾形态 只允许一轮，且无新证据不许放宽结论
帮助中心问答 针对本张发票引用制度条款作答 问答空间是开放的 回答必须能展开制度原文

一句话概括：规则负责「判得准」，AI 负责「看得懂、说得清」，校验层负责「不许胡说」。 三者缺一，这个系统要么不可信，要么不实用。

7.1 发票识别

  • 功能：一次可选多张，XML 数电票直读法定原件；版式 PDF 用坐标法还原明细表；图片走 OCR 兜底。
  • 没有 AI：识别本身是确定性问题，本就不该用 AI——这是刻意设计。
  • AI 增量：对 PDF 中被粘成 12437.735849056604 这类脏数据，程序用穷举切分求「数量 × 单价 ≈ 金额」的最小误差解，把不可读的表格救回来。

7.2 基础合规校验（12 项）

  • 功能：抬头、税号、金额勾稽、明细汇总、单价、日期期限、号码格式、重复报销、税率、大小写一致等，逐项给出通过 / 不通过与原因。
  • AI 增量：刻意不用 AI。有唯一答案的事交给代码，才谈得上「快」和「确定」。它是整个流程的准入闸门。

7.3 行为风控（6 项）

  • 功能：重复报销、连号发票、拆分报销、金额临界、高频报销、员工行为画像。
  • AI 增量：风控结果作为上下文注入 Agent 提示词，并要求结论点名风险，避免出现「模型装作没看见」。重复、连号、拆分是行业公认的舞弊模式，这条决定了作品「解决的是真问题」。

7.4 事由语义审核（LLM 语义判断）

  • 功能：员工填完报销事由后，由一个独立的 LLM 环节判断「报销事由 ↔ 发票内容（销售方、项目名称）↔ 所选费用类型」三者是否逻辑一致，输出通过 / 警告 / 不通过及理由。
  • 没有 AI：这是纯语义判断，规则写不出来。「住宿费发票却写办公用品采购」这类不一致，只有模型能发现。
  • AI 增量：把「事由是否说得通」这道判断从人工环节前移到填单环节。事由不通过时弹出对话框拦截保存，员工可查看详细分析后修正，或显式选择「确认保存草稿」；语义审核结果有缓存，避免同一份内容反复调用模型。
  • 与 Agent 终审的分工：事由语义审核是单点判断（只看事由与票面），Agent 终审是综合裁决（还要结合费用标准、风控制结果、制度条款）。

7.5 费用标准工具（AI 唯一的数值来源）

  • 功能：住宿（城市三级 × 职级三档，未列城市按其他城市处理）、市内交通 80 元/天、伙食补助 100 / 120 元/天，并返回命中的条款出处。
  • 没有 AI：只能给出「超标 80 元」这种数字，解释不了「超标了怎么申诉」。
  • AI 增量：模型自主决定该不该调这个工具、参数怎么填、结果怎么解读。

7.6 制度 RAG 检索

  • 功能：双路召回后加权融合，返回条款原文与出处。
  • AI 增量：让「依据」可被引用、可展开，而不是让模型凭记忆背诵制度条文。

7.7 ReviewAgent 终审（AI 核心）

  • 功能：ReAct 循环，自主决定调用费用标准工具还是制度检索，综合风控结果与制度给出结构化裁决。
  • 没有 AI：只能输出「超标 80 元」这类数字，无法处理「事由与发票内容不匹配」「这笔聚餐算不算业务招待」这类语义判断。
  • AI 增量：这是规则唯一做不到的部分。在 12 条「金额完全在标准内、只能靠语义判断」的对抗样本上，纯规则引擎判对 0 条，Agent 判对 12 条。
  • 界面可见：步骤序号 · 工具名 · 参数 · 返回值 · 制度原文折叠面板。

7.8 结构化裁决

  • 功能：把结论、费用类型、理由、证据链、条款引用、置信度、是否转人工固化成字段。
  • AI 增量：消除解析歧义，并让下游程序可以做逐条对账——没有结构化，防幻觉校验根本无从下手。

7.9 防幻觉校验（13 项交叉核对）

  • 功能：结论与工具返回值是否矛盾、引用的工具是否真的调用过、金额能否溯源、条款引用是否命中检索原文、风控高危是否被吸收……
  • AI 增量：这是「敢于让模型下结论」的前提条件。没有这一层，系统的可信度等于模型的自觉程度。

7.10 反思机制

  • 功能：工具返回与预期矛盾时，Agent 自主追加检索（例如查「超标了怎么申诉」）并修正结论。
  • AI 增量：把「AI 自主纠错」做成可控的三步机制，而不是靠提示词祈祷；REFLECTION_MAX_ROUNDS = 1 卡住成本，避免反复循环。

7.11 票夹 · 报销单 · 详情

  • 票夹：发票卡片网格，固定尺寸；卡片显示可辨识信息（销售方、金额、上传时间）；点击进详情；右上角上传新发票。
  • 报销单：统一主表 + 分类扩展（住宿 / 餐饮 / 交通 / 材料 / 办公用品 / 其他），发票上已有的商品明细自动注入；发票号码由系统带出，用户不手填；同一次出差的多张发票用行程号分组。
  • 发票详情页：完整审核明细、完整解析数据、下载发票原文件、从票夹移除；基础校验不通过时「填写报销单」按钮置灰并说明原因。

报销单详情页：审核结论、AI 审核决策过程（Agent 思考与工具调用逐步展开）、制度依据引用溯源（结论引用的条款 ↔ 检索原文并排对照）、防幻觉校验报告（逐项检查明细）、咨询 AI 审核员、人工申诉、以及编辑 / 删除 / 重新提交。

7.12 帮助中心

  • 功能：左侧为制度文档导航（可直接浏览知识库原文），右侧分「制度问答」与「我的发票咨询」两个页签。制度问答提供快捷问题入口，每条回答下方可展开本次引用的制度原文；发票咨询携带本张发票的识别与校验结果，并支持「结束咨询，返回上传页」。
  • AI 增量：员工追问「为什么不通过」，系统当场检索并引用条款作答，且每条回答都能翻回原文，减少财务的口头解释工作。

八、使用说明

8.1 用户操作流程

上传发票（可多张）
   → 逐张识别 + 12 项基础校验
   → 查看分档结果（识别失败 / 校验不通过 / 有警告 / 完全通过）
   → 存入票夹
   → 填写报销单（统一主表 + 分类扩展，明细自动注入）
   → 事由语义审核
   → 6 项行为风控
   → Agent 终审（调用费用标准工具 + 检索制度原文）
   → 防幻觉校验（矛盾则改写或转人工）
   → 查看依据 / 追问 / 申诉

九、应用前景

9.1 落地路径

  1. 校园试点：对接财务处报销窗口，先跑差旅住宿与办公费两类高频场景。
  2. 中小企业：按部门开通，制度文档由企业自行替换知识库（Markdown 即可，无需开发）。
  3. ISV / 代理：作为现有 OA 或费控系统的预审插件，不替换原有审批流。

9.2 推广条件

  • 政策窗口：数电票以 XML 为法定原件，为「直解析」提供了合法性与合理性基础。
  • 差异卖点：可解释预审，而不是黑盒「AI 说不行」；每一条驳回都有条款出处。
  • 风险可控：模型误判由人审兜底；密钥与账号需按生产级标准管控；原件只存本单位库。

9.3 推广潜力

高校与中小企业的共同点是制度相对稳定、单据量集中、缺乏专职费控人员，恰好是「规则 + 少量语义判断」这套架构最经济的适用区间。制度替换成本极低（改 Markdown 即可），有利于规模化复制。

十、商业模式

客户 收费方式 说明
高校 按学年服务费 + 实施培训费 一次性对接，年度维护
中小企业 按座席或按单据量 基础规则包免费，Agent 与知识库更新收费

数据边界：不靠出售发票数据获利；原件与解析结果只存本单位数据库。
